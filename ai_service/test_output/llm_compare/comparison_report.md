## 四、综合结论

### 4.1 核心数据

| 维度 | 云端 (DeepSeek) | 本地 (Ollama qwen2.5-7b) |
|------|----------------|--------------------------|
| 成功率 | 4/4 (100%) | 3/4 Ollama 直调成功 + 1/4 降级 fallback |
| 平均耗时 | 9.64s | 26.40s（含 fallback 的 29s） |
| 平均输出长度 | 1450字 | 1053字（含 fallback 的 175字） |
| 本地/云端耗时比 | 1.0x | 2.7x |
| 成本 | 按 Token 计费 | 零成本（仅电费） |
| 隐私 | 数据上传云端 | 完全离线 |
| 部署门槛 | 仅需 API Key | 需 6GB+ 显存 GPU |

### 4.2 关键发现

**1. 健康咨询对话场景：本地 Ollama 超时降级**
- 该场景的 prompt 最复杂（系统提示 + 知识库检索 5 条结果 + 用户健康快照 + NLU 解析），总 token 数接近 2048 上下文上限
- Ollama 在 30s 超时内未能完成生成，触发 orchestrator 降级到 local_fallback_engine
- 云端 DeepSeek 无上下文限制，17.8s 返回 1339 字详尽建议，引用了《中国血脂异常食养指南》

**2. 结构化 Agent 任务：本地可胜任但质量略逊**
- 饮食方案、运动方案、食材推荐 3 个场景，Ollama 均成功输出合法 JSON
- 但本地输出存在**模式重复**问题（如运动方案中"采用有节奏的中速游泳/跑步"重复出现）
- 云端输出更个性化（如运动方案针对高血压患者标注"心率控制在100-120"和"血压监测"）

**3. 营养数值准确性**
- 饮食方案：云端 total_calories=2250（符合孕期推荐），本地=2750（偏高）
- 食材推荐：两者卡路里估算接近（云端 350 vs 本地 450），差异在合理范围

**4. 知识库引用**
- 云端能主动引用知识库中的指南名称（如《中国血脂异常食养指南（2023版）》）
- 本地虽然检索到了相同的知识库内容，但在回答中未显式引用来源

### 4.3 适用场景建议

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 健康咨询对话（复杂 prompt） | 云端 | 本地 7B 模型上下文不足，易超时 |
| 饮食/运动方案生成 | 两者皆可 | 本地可胜任，云端质量略优 |
| 食材菜谱推荐 | 两者皆可 | 本地输出质量接近云端 |
| 离线/隐私敏感场景 | 本地 | 数据不出本地 |
| 高并发场景 | 云端 | 本地单卡仅支持串行，并发能力有限 |
| 成本敏感场景 | 本地 | 零 API 费用 |

### 4.4 本地大模型优化方向

若要提升本地大模型表现，建议：
1. **扩大上下文窗口**：将 num_ctx 从 2048 提升到 4096（需 8GB+ 显存），避免复杂 prompt 超时
2. **增加超时阈值**：本地模式 LLM_TIMEOUT 从 30s 提升到 60s
3. **精简 prompt**：对本地模式裁剪知识库检索结果数量（top_k 从 5 降到 3）
4. **升级模型**：换用 qwen2.5:14b（需 12GB+ 显存）可显著提升输出质量
5. **混合架构**：复杂对话走云端，简单结构化任务走本地，兼顾质量与成本
